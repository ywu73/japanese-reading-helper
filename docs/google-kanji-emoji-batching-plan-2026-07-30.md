# Google 汉字罗马音 emoji 分隔符批量 — 执行文档（2026-07-30）

## 目的与决策边界

本文档记录一个待实施方案：在保持 Google 匿名无 key 接口
（`translate.googleapis.com/translate_a/single`，`client=gtx`）的前提下，把当前
**逐词一请求**的汉字罗马音路径，改为**用自定义分隔符 🧩 连接多词的批量快速路径 +
逐词降级兜底**。

这是一个**经过校验、允许失败降级的经验性协议**，不是 Google 官方保证的批量格式。
`translate_a/single` 是未公开接口，Google 不承诺永远原样保留 🧩。因此实现必须
fail-closed，任一校验不过即整批放弃并退回逐词。

本文档只定义实施方案与验证边界，不改变产品边界：在线汉字罗马音仍受精确 origin 启用
与 provider 选择约束。是否实施、何时实施，由后续明确决定。

## 已验证事实（2026-07-30 实时探针，经本地代理）

所有样本以 `sl=ja&tl=ja&dt=t&dt=rm`、🧩 连接、慢速发送（间隔 4s 以排除限流假象）取得。

### 分隔符对比：🧩 显著优于 `.`

| 样本 | `.` 旧结果 | 🧩 新结果 | 段数==词数 |
| --- | --- | --- | --- |
| `一 / 二 / 三` | 整批 `<none>`（被当版本号） | `Ichi 🧩 ni 🧩 san` | ✅ 3 |
| `木 / 金 / 土 / 日` | `Ki.-Kin` 变形 | `Ki 🧩 kin 🧩 tsuchi 🧩 hi` | ✅ 4 |
| `神奈川県 / 大阪市 / 東京都` | 可用 | `Kanagawa ken 🧩 Ōsaka ichi 🧩 Tōkyōto` | ✅ 3 |
| `人々 / 食べる / 取り締まり / 令和` | — | `Hitobito 🧩 taberu 🧩 torishimari 🧩 ryō wa` | ✅ 4 |
| 20 词长批（山川海空…石森） | `.` 变形 | 🧩 一个不丢，20 段 | ✅ 20 |

`.` 的两个死因（数字/序数序列整批失败、分隔符被改写成 `.-`）在 🧩 下均消失：emoji
不被当作句读、数字或版本号，因此原样保留。所有样本段数恒等于词数。

### 压测暴露的两个关键点（资料附带的 parser 会踩）

**A. 罗马音字段位置随 `tl` 与置信度变化。**

```
神奈川県…  → [null, null, "Kanagawa ken 🧩…", "Kanagawa ken 🧩…"]   罗马音在 [2] 和 [3]
第一🧩第二… → [null, null, "Daiichi 🧩 daini 🧩 daisan"]              只在 [2]，无 [3]
```

`tl=ja` 下罗马音**恒定出现在 `item[2]`**；低置信度返回（如 `第一 / 令和`）只填 `[2]`，
不填 `[3]`。只查 `item[3]` 的 parser 会在这些输入上误判"找不到罗马音"而整批失败、白白
降级。**正确实现认 `item[2]`。**（注意：现网 `tl=en` 版罗马音在 `[3]`，与此不同。）

**B. 分段内可能混入白名单外字符。**

20 词批中 `日` 被转成 `Ni~Tsu`（含 `~`）。段数仍对齐（安全），但该段过不了
`SAFE_ROMAJI`。需"只跳该段、保留其余"，而非整批弃。

### 与 Bing 同源的既有特性

批量语境下（`usedLLM`）个别词读音可能与单发不同。这不是错配，是读音风格差异，与已上线
的 Bing 批量同性质。

## 工程判断（基于事实的分析，非既成结论）

🧩 方案可行，可作为"带严格校验的批量快速路径"。相比已上线的 Bing 强校验批量，它有两处
结构性偏弱，必须如实标注并以降级兜底：

- **无逐词原文锚点**：Google 罗马音段不含原文，只能靠"段数==词数 + 位置"对齐，不如
  Bing 的逐行 echo 校验强。理论上"某处吞一个 🧩 + 另一处增一个"方向相消会造成错配；
  压测（含 20 词）未见 🧩 被吞或增，概率极低但非零。
- **依赖非契约行为**：接口未公开，🧩 保留行为可能随时变化。故必须 fail-closed + 逐词
  降级。

上述弱点决定了：批量是"快速路径"，逐词是"正确性底座"，两者缺一不可。

## 实施设计

### 请求

- 端点/鉴权不变：`client=gtx`、`sl=ja`、`tl=ja`、`dt=t`、`dt=rm`、`q=<🧩 连接>`。
- 复用批量骨架（对齐 Bing/片假名）：`buildBatches`（≤50 词、编码长度预算、250ms 间隔、
  8000ms 超时、`anonymous:true`、`redirect:"error"`、URL/finalUrl 校验）。
- 词资格保持现状：含汉字、≤200 字符、无控制字符、无首尾空白；额外要求词本身不含 🧩。

### 解析（修正版，fail-closed）

1. `payload[2] === "ja"`，否则整批弃。
2. 原文回显条目唯一，且**完整等于**请求的 🧩 连接串，否则整批弃。
3. 罗马音字段认 **`item[2]`**（唯一一个），否则整批弃。
4. 按 🧩 切分并 `trim()` 每段。
5. **段数必须等于词数**，否则整批弃（绝不错位映射）。
6. **逐段** `SAFE_ROMAJI` 校验（白名单需加入空格，因 `Kanagawa ken` 含空格）；不安全
   或残留 🧩 的段**只跳该词**，保留其余对齐段。

### 降级

整批失败（段数不符 / 无回显 / 无唯一罗马音 / HTTP 错误 / 429 / 超时 / 结构变化）→ 退回
**现有逐词逻辑**（每词一请求、250ms 间隔、`tl=en`、`item[3]` 解析）。降级路径即当前已
上线实现，零新增正确性风险。

### SAFE_ROMAJI 变化

现网：`/^[A-Za-zĀĪŪĒŌāīūēō'’-]+$/u`（逐词，无内部空格）。
批量段含词内空格（`Kanagawa ken`），需新增空格：
`/^[A-Za-zĀĪŪĒŌāīūēō'’ -]+$/u`。仅用于批量段校验；逐词降级路径保持原白名单不变。

- 不引入 `tk` 签名路径（需逆向 Google 签名 + 维护动态 TKK，脆弱且越界）。
- 不改产品边界、不新增端点、不做 provider 间自动切换、不提交页面周边文本。
- 未验证：Tampermonkey 真实 `GM_xmlhttpRequest` 传输、🧩 长期保留稳定性、Google 匿名
  限流的实际阈值、大规模真实页面表现。故本方案在这些方面属经验性协议，发布仍需通过既有
  人工与发布门槛。
